# ADR-017 — Topology identity, confidence, and cardinality

Status: accepted for Phase 2A

Services use the inventory's shared canonical logical-key function: a valid `service.name`, optionally prefixed by canonical `service.namespace` with `.`. Empty and absent namespaces are equivalent; `unknown_service` identities and fuzzy matching are rejected. HTTP endpoints are `METHOD http.route` templates and RPC endpoints are `rpc.service/rpc.method`; span names and concrete URL paths never become endpoint identity.

Dependencies come only from CLIENT or PRODUCER spans. Identity priority is a directly associated remote SERVER/CONSUMER, `peer.service`, database/messaging/RPC semantic attributes, then `server.address`. A direct association is either parent/child propagation for synchronous CLIENT/SERVER traffic or a CONSUMER `SpanLink` to a PRODUCER for asynchronous traffic. Link attributes are discarded; only bounded, non-zero trace/span references are retained in memory while decoding. Semantic fallback is a distinct, weaker source of identity and is never presented as direct propagation.

Exactly one directly associated remote service produces HIGH confidence when comparable `peer.service` and `rpc.service` metadata agree or are absent. A contradictory semantic target does not create a second edge: the directly observed target wins, the basis records the conflict, the limitation is preserved, and confidence is capped at MEDIUM. Multiple directly associated service identities are ambiguous and are never selected by input order; a safe semantic fallback may still produce a MEDIUM edge with an explicit ambiguity limitation. `dropped_links_count` also caps an otherwise linked relation at MEDIUM and records incomplete association evidence. Insufficient destination data creates no edge.

Target resolution is temporal. The nullable resolved service belongs to each `service_dependency_observations` row, not to global dependency identity. A future window that observes a service cannot change the target node, confidence, limitations, evidence, or IDs of an older observation. The target must be a service in the same normalized environment/window and its logical key must equal the service dependency logical key.

Relations are always `OBSERVED`: supported direct pairs are HIGH unless a contradiction or link-quality limitation caps them, declared semantic identity is MEDIUM, address-only identity is LOW, and UNKNOWN creates no edge. The algorithm is `otel-topology/v1`; no OTel edge is EXACT and no relation asserts causality.

`request_count` and `error_count` describe the observed operation represented by each dependency observation. A directly associated synchronous CLIENT→SERVER pair contributes exactly one request: it is an error when either span has `Status=ERROR` or when either allowlisted `http.response.status_code` is at least 500. This union is counted once, independent of span order. Semantic fallbacks do not borrow error state from incompatible or unassociated spans. Asynchronous PRODUCER→CONSUMER observations retain outbound (PRODUCER) error semantics until a separate asynchronous operation contract is defined.

Windows are half-open `[start,end)`. SERVER durations use deterministic nearest-rank p50/p95/p99. Coverage remains unknown and `is_complete=false` because sampling coverage is not known. Hard ingestion limits are 64 MiB/file, 1 MiB/line, 10,000 lines, 100,000 spans, 32 links/span, 100,000 links/snapshot, 1,000 services, 5,000 endpoints, 5,000 dependencies, and four evidence fingerprints per observation. Graph queries accept 1..1,000 nodes and fetch at most ten temporal edges per requested node (never more than 10,000); either limit sets `truncated` and emits a warning. Exceeding an ingestion limit aborts the entire operation.

Only the documented resource/span allowlists cross the decoder boundary. Raw trace/span IDs, link IDs, link attributes, events, bodies, statements, URLs, headers, baggage, unknown attributes, and full attribute maps are discarded. Reproducible evidence uses the versioned framing `sha256-v1 NUL source_hash_utf8 NUL trace_id_binary NUL span_id_binary`; SHA-256 is calculated over those exact bytes and rendered as `sha256-v1:<lowercase hex>`. The NUL separators, binary (not hex/base64) identifiers, and version prefix are part of the contract. Claims are fixed vocabulary (`outbound client span`, `linked remote server span`, `outbound producer span`, `linked consumer span`) and never contain source values. The fixed vector for source hash `sha256:` followed by 64 `a` characters, trace bytes `00..0f`, and span bytes `00..07` is `sha256-v1:1b6c39feeee44366a02aebfb1dd30f9b72e4d5c73115265f6d8af056f3795b9d`.
